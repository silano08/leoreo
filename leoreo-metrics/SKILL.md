# Leoreo Metrics — 계측과 실험

`leoreo` 본체는 "전환율이 가장 낮은 구간이 병목"이라 말하고 "데이터 없이 단정하지 않는다"고 규정합니다. 이 스킬은 **그 데이터를 만드는 쪽**입니다. 진단할 숫자가 없으면 병목 진단도, 돈-체크 테이블의 기대 아웃풋도, 출시 후 측정 계획도 전부 추측이 됩니다.

## 세 가지 원칙

1. **지표는 판단에 쓰일 때만 만듭니다.** "이 숫자가 어떻게 나오면 우리가 무엇을 다르게 할 것인가"에 답이 없으면 그 지표는 만들지 않습니다. 대시보드가 커질수록 보는 사람은 줄어듭니다.
2. **돈으로 끝나는 지표를 위에 둡니다.** 가입자 총합·페이지뷰 같은 허영 지표(vanity metric)는 대시보드 아래로 내리거나 뺍니다. 위쪽은 결제 전환, 코호트 리텐션, MRR 이동분해 자리입니다.
3. **돈 지표와 행동 지표는 출처를 분리합니다.** 매출은 결제·구독 원장 테이블에서, 행동은 이벤트 로그에서 뽑습니다. 섞으면 숫자가 안 맞고, 안 맞는 대시보드는 아무도 안 믿습니다.

## 1단계 — 무엇을 잴지 먼저 정합니다

이벤트를 심기 전에 "어떤 판단을 하려는가"부터 씁니다. 판단이 없으면 계측도 없습니다.

| 하려는 판단 | 필요한 지표 | 최소로 심을 이벤트 |
|---|---|---|
| 온보딩이 병목인가 | 단계별 완료율, time-to-value(첫 가치까지 걸린 시간) | 가입 완료 / 각 온보딩 단계 완료 / 아하 모먼트 도달 |
| 결제가 병목인가 | 가격 조회→결제 시작→결제 완료 전환율 | 요금제 조회 / 결제 시작 / 결제 성공 / 결제 실패(사유 포함) |
| 리텐션이 새는가 | 가입 코호트별 D7·D30 잔존, 월별 이탈률 | 핵심 행동 1개(그 서비스를 쓴다고 말할 수 있는 행동) |
| 확장 매출이 도는가 | NRR, 업그레이드·다운그레이드 건수 | 플랜 변경(이전 플랜·다음 플랜·사유) |
| 이 기능이 효과가 있었나 | 실험군/대조군 목표 지표 차이 | 노출(exposure) + 목표 전환 + 가드레일 |

## 2단계 — 이벤트 택소노미(이름 규칙과 스키마)

- **이름은 `대상_행동` 과거형 하나로 고정합니다.** `checkout_started`, `subscription_upgraded` 처럼요. 한 팀 안에서 `Click Pay`, `pay_click`, `PaymentStart`가 섞이는 순간 분석이 불가능해집니다.
- **모든 이벤트에 공통 프로퍼티**를 강제합니다: 이벤트 이름, 사용자 ID, 비로그인 식별자, **서버 기준 시각**, 발생 위치(web/app/server), 스키마 버전. 클라이언트 시각은 기기 시계가 틀려서 코호트를 망칩니다.
- **돈과 관련된 이벤트는 반드시 서버에서 보냅니다.** 광고 차단·앱 강제종료·네트워크 끊김으로 클라이언트 이벤트는 10~30%가 유실됩니다. 결제·구독·플랜 변경은 서버 이벤트 또는 결제 원장에서 뽑습니다.
- **AARRR 단계마다 이벤트 1~3개면 충분합니다.** 처음부터 200개를 심는 것보다 15개를 정확히 심는 쪽이 낫습니다.

흔한 실패는 넷입니다. 이벤트 폭발(쓰지 않는 이벤트가 대부분), 클라이언트 전용 수집, 프로퍼티에 자유 서술 문자열 넣기(집계 불가), 이름을 조용히 바꾸기(과거 데이터와 단절 — 바꿔야 하면 새 이름 + 버전 필드).

개인정보는 계측 단계에서 걸러냅니다. 주민번호·카드번호·연락처를 이벤트 프로퍼티에 넣지 않고, 필요하면 해시된 ID만 보냅니다. 국내 서비스는 개인정보처리방침에 수집 항목과 위탁받는 분석 도구를 적어야 합니다.

## 3단계 — 코호트와 퍼널

- **리텐션은 반드시 코호트로 봅니다.** 전체 활성 사용자 수는 신규 유입이 이탈을 가려서 병이 안 보입니다. 가입 주(월) 단위로 묶어 N일 차 잔존을 표로 만들면 "제품이 나아지고 있는가"가 대각선으로 보입니다.
- **리텐션 곡선이 평평해지는 지점이 있는지**를 봅니다. 계속 0으로 떨어지면 아직 제품-시장 적합(PMF) 이전입니다.
- **퍼널은 단계 사이 전환율로 봅니다.** 절대 수가 아니라 각 구간 전환율에서 가장 낮은 곳이 `leoreo`가 말하는 병목입니다.
- 실행 가능한 SQL 템플릿(코호트 리텐션, 퍼널, MRR 분해)은 `references/instrumentation.md`에 있습니다.

## 4단계 — 매출 지표

- **MRR 이동분해**가 매출 대시보드의 기본형입니다: `기초 MRR + 신규 + 확장 − 축소 − 이탈 + 재활성 = 기말 MRR`. 좌우가 맞지 않으면 대시보드가 아니라 버그입니다.
- **NRR**(기존 고객만으로 매출이 얼마나 늘었나)은 신규 고객을 빼고 계산합니다. 100% 미만이면 밑 빠진 독입니다.
- **LTV:CAC와 CAC 회수기간은 같이 봅니다.** 비율이 좋아도 회수기간이 길면 현금이 먼저 마릅니다. 공식과 건강 범위는 `leoreo` 부록 `references/global-frameworks.md`의 지표 섹션에 있습니다.
- 원가를 반영한 마진 지표(코호트별 총마진, 요청당 원가)는 `leoreo-cost`가 담당합니다.

## 5단계 — A/B 테스트

- **시작 전에 표본 크기를 계산합니다.** 현재 전환율과 "이 정도는 움직여야 의미 있다"는 최소 검출 효과(MDE)를 정하면 필요한 기간이 나옵니다. 계산해 보고 3개월이 걸린다면 그 실험은 하지 않는 게 맞습니다.
- **기간을 미리 못 박고 중간에 보고 멈추지 않습니다.** 유의미해질 때까지 매일 들여다보다 멈추면(peeking) 거짓 양성이 크게 늘어납니다. 최소 한 주 단위(요일 효과 제거)로 돌립니다.
- **가드레일 지표를 함께 봅니다.** 결제 전환이 올라도 환불률·이탈률·응답속도가 나빠졌으면 이긴 게 아닙니다.
- **트래픽이 적으면 A/B를 억지로 하지 않습니다.** 사전-사후 비교, 순차 롤아웃(당근 원칙의 좁은 세그먼트 배포), 5~10명 질적 인터뷰가 더 정직한 선택입니다. 상세는 `references/experiments.md`.

## 도구 선택

| 상황 | 선택 |
|---|---|
| 아직 아무것도 없음, 빨리 보고 싶음 | PostHog나 Amplitude 무료 티어로 시작 — 직접 만들지 않습니다 |
| 제품 행동 분석 중심 | Amplitude / Mixpanel |
| 세션 리플레이·플래그·실험까지 한 곳에서 | PostHog |
| 마케팅 채널 어트리뷰션 필요 | GA4를 채널 분석 용도로만 병행 |
| 매출·정산 지표 | 분석 도구 말고 **자체 DB(결제 원장) 기준**. 분석 도구 숫자는 매출 보고용으로 쓰지 않습니다 |

`leoreo` 원칙("결제·인증·모니터링은 사는 게 기본")이 계측 도구에도 그대로 적용됩니다. 자체 분석 파이프라인은 차별화 지점이 아닙니다.

## leoreo와의 연결

- 돈-체크 테이블의 **측정 계획** 칸을 이 스킬이 채웁니다. 기능 착수 승인 조건에 "심을 이벤트와 볼 쿼리가 정해졌는가"를 넣습니다.
- **Kill 기준의 숫자는 측정 가능해야 합니다.** 잴 수 없는 kill 기준은 없는 것과 같습니다.
- 원가·마진은 `leoreo-cost`, 리텐션 개선 실행은 `leoreo-retain`으로 넘어갑니다.

## 출력 규칙

- 사용자와 소통할 때는 되도록 쉬운 말을 씁니다. 코호트·MDE 같은 용어가 필요하면 첫 등장에 괄호로 풀이를 붙입니다(예: 코호트(같은 시기에 들어온 사용자 묶음), MDE(이 정도는 움직여야 의미 있다고 정한 최소 변화폭)).
- 지표 설계 요청이면 **"어떤 판단을 하려는가"를 먼저 확인**하고, 판단 없이 지표만 늘리자는 요청은 되묻습니다.
- 계측 요청이면 이벤트 이름·프로퍼티·수집 위치(클라이언트/서버)를 표로 확정해 냅니다. 돈 관련 이벤트가 클라이언트에만 있으면 지적합니다.
- 실험 요청이면 표본 크기와 예상 소요 기간을 먼저 계산해 보여주고, 기간이 비현실적이면 A/B 대신 다른 방법을 제안합니다.
- 결론은 항상 셋 중 하나입니다: **지금 계측한다 / 판단이 먼저다 / 이 지표는 안 만든다** — 근거와 함께.
