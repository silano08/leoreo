# 엔터프라이즈 준비도 부록 — 구현 노트와 체크리스트

> 인증 제도·법령·고객사 요구는 2025~2026년 기준이며 바뀝니다. 심사·계약 직전에 원문과 고객사 양식으로 재확인합니다.

## 1. SSO (SAML 2.0 / OIDC)

- **SAML 2.0을 먼저 지원합니다.** 국내 대기업 사내 계정 시스템(IdP)은 여전히 SAML 중심입니다. OIDC는 그다음.
- **고객사 관리자가 직접 설정하게 만듭니다.** 메타데이터 URL 입력 또는 XML 업로드, 연결 테스트 버튼, 속성 매핑 화면. 우리가 매번 수동으로 붙여 주는 구조는 고객이 늘면 무너집니다.
- **구현 주의점**
  - 기존 이메일·비밀번호 계정과 SSO 계정을 **어떻게 병합할지 먼저 정합니다.** 나중에 정하면 중복 계정 사고가 납니다.
  - 도메인 기반 자동 라우팅(회사 이메일로 들어오면 해당 IdP로): 도메인 소유 확인이 없으면 계정 탈취 경로가 됩니다.
  - **SSO 강제(SSO enforcement)** 옵션이 실제 요구사항입니다. 관리자가 켜면 그 조직 구성원은 비밀번호 로그인이 막혀야 합니다.
  - 관리자용 비상 접근 경로를 하나 남깁니다. IdP 장애 시 아무도 못 들어오는 상황을 막습니다.
- **자체 구현 vs 구매**: 차별화 지점이 아니므로 사는 게 기본입니다. 국내 리전·망분리 요건이 있으면 외부 서비스가 막힐 수 있으니 요건을 먼저 확인합니다.

## 2. SCIM (사용자 자동 동기화)

- 고객사 인사 시스템에서 입사·부서이동·퇴사가 일어나면 우리 서비스 계정도 자동으로 맞춰지는 규격입니다.
- **보안팀이 특히 요구합니다.** 퇴사자 계정이 남아 있는 것이 감사에서 지적되는 대표 항목입니다.
- **좌석 과금과 직결됩니다.** 실제 활성 사용자가 정확해져서 좌석제 정산 분쟁이 줄어듭니다 — `leoreo-model`의 과금 단위와 연결됩니다.
- **구현 주의점**: 비활성화(deprovision)를 **삭제가 아니라 비활성으로** 처리합니다. 그 사용자가 만든 데이터가 사라지면 안 됩니다. 재활성화 경로도 필요합니다.

## 3. 감사로그 (고객이 직접 조회)

우리 내부 로그가 아니라 **고객사 관리자가 화면에서 보고 내보낼 수 있는** 로그입니다. 설계를 나중에 바꾸기 어려우므로 이벤트 정의를 처음에 잘 합니다.

### 반드시 남겨야 하는 이벤트

| 분류 | 이벤트 |
|---|---|
| 인증 | 로그인 성공·실패, 로그아웃, 비밀번호 변경, MFA 등록·해제 |
| 계정 | 사용자 초대·생성·비활성화·삭제, 역할 변경 |
| 권한 | 권한 부여·회수, 관리자 승격 |
| 설정 | SSO 설정 변경, 보안 정책 변경, API 키 발급·폐기 |
| 데이터 | 민감 데이터 조회·내보내기·대량 삭제 |
| 결제 | 플랜 변경, 결제수단 변경 |
| 연동 | 외부 연동 추가·제거, 웹훅 등록 |

### 각 항목에 필요한 필드
발생 시각(서버 기준, 변경 불가), 행위자, 대상, 행위, 결과(성공/실패), IP·기기 정보, 그리고 변경 전후 값.

### 구현 주의점
- **불변(append-only)이어야 합니다.** 수정·삭제가 가능하면 감사 증적으로서 가치가 없습니다.
- 보관 기간을 정하고 플랜별로 차등할 수 있게 둡니다(예: 기본 90일, 엔터프라이즈 1년). 보관 원가는 `leoreo-cost`에 반영합니다.
- 내보내기(CSV·API)가 실제 요구사항입니다. 화면 조회만으로는 부족합니다.
- **내부 직원의 고객 데이터 접근 로그**는 이것과 별개로 필요합니다. "우리 직원이 고객 데이터를 언제 봤는가"를 묻는 질의서 항목이 흔합니다.

## 4. RBAC (역할별 권한)

- 최소 3단(관리자 / 편집자 / 조회자)에서 시작하고, 요구가 반복되면 세분화합니다. 처음부터 완전한 권한 체계를 만들려다 출시가 늦어지는 게 더 흔한 실패입니다.
- **IdP 그룹 → 우리 역할 매핑**이 실제 요구사항입니다. 고객사 AD·IdP 그룹 이름으로 역할이 자동 부여돼야 합니다.
- 권한 판정은 **서버 단일 지점**에서 합니다. 화면에서 버튼을 숨기는 것은 UX이지 보안이 아닙니다 — `leoreo-pay`의 엔타이틀먼트 규칙과 같습니다.
- 조직·워크스페이스 계층이 필요한지 초기에 정합니다. 나중에 넣으려면 데이터 모델을 갈아야 합니다.

## 5. ISMS-P 준비 체크리스트

정보보호 및 개인정보보호 관리체계 인증입니다. 대기업·공공 납품에서 요구되거나 가점이 됩니다.

**시작 전 판단**
- [ ] 실제로 요구받았는가, 아니면 있으면 좋겠다는 추측인가
- [ ] 의무 대상인가 (매출·이용자 수 기준의 의무 대상 요건이 있습니다 — 해당 여부 확인 필요)
- [ ] 준비 비용(컨설팅·심사 실비·내부 인력 수개월)이 막힌 딜 금액보다 작은가
- [ ] 매년 사후심사, 3년마다 갱신심사 부담을 감당할 수 있는가

**개발팀이 준비하는 항목** (대표적인 것만)
- [ ] 접근 통제: 권한 부여·회수 절차와 기록, 관리자 접근 이력
- [ ] 암호화: 전송 구간(HTTPS)과 저장 시 개인정보 암호화
- [ ] 로그 관리: 보존 기간, 위변조 방지
- [ ] 백업·복구: 절차 문서와 복구 훈련 기록
- [ ] 취약점 점검: 정기 점검과 조치 이력
- [ ] 변경 관리: 배포 승인 절차, 코드 리뷰 기록
- [ ] 개인정보 흐름도: 수집·저장·이용·파기 전 과정

인증은 문서 작업이 절반 이상입니다. 개발보다 **기록을 남기는 습관**이 통과를 좌우합니다.

## 6. 보안질의서 자주 나오는 항목

고객사마다 양식은 다르지만 묻는 것은 대체로 같습니다. 아래에 대한 표준 답변을 한 번 만들어 두고 재사용합니다.

- 데이터가 어디에 저장되는가 (리전, 클라우드 사업자, 국외 이전 여부)
- 저장·전송 시 암호화 방식
- 접근 통제: 누가 고객 데이터에 접근할 수 있고 어떻게 기록되는가
- 백업 주기와 보관 기간, 복구 목표 시간(RTO/RPO)
- 사고 발생 시 통지 절차와 기한
- 하위 처리자(재위탁) 목록 — 쓰고 있는 클라우드·SaaS 전체
- 계정·인증 정책 (비밀번호 규칙, MFA, 세션 만료)
- 취약점 점검·모의해킹 수행 여부와 주기
- 개발 보안: 코드 리뷰, 의존성 취약점 점검, 배포 승인
- 데이터 삭제·반출 요청 처리 방법과 기한
- 가용성 실적과 SLA
- 보유 인증 (ISMS-P, ISO 27001, SOC 2 등)

**만들어 두면 좋은 자산 3종**: 보안 백서(위 항목의 답변을 담은 문서), 아키텍처·데이터 흐름도, 하위 처리자 공개 페이지. 이 셋이 있으면 질의서 대응 시간이 며칠에서 몇 시간으로 줄어듭니다.

## 7. 국내 B2B 도입 흐름과 개발 산출물

| 단계 | 막히는 이유 | 미리 준비할 것 |
|---|---|---|
| 실무자 평가 | 기능·사용성 | 체험 환경, 온보딩 |
| 보안 심사 | 질의서·인증 | 6절 자산 3종, SSO, 감사로그 |
| 법무 검토 | 계약 조항 | 표준 약관, DPA, 하위 처리자 목록 |
| 구매·재무 | 결제·정산 방식 | 전자세금계산서, 견적서, 사업자 서류 |
| 전자결재 | 내부 승인 | 도입 효과 자료(실무자가 품의서에 쓸 근거) |

마지막 항목이 자주 빠집니다. **챔피언(내부 지지자)이 품의서에 붙일 수 있는 자료**(도입 효과 추정, 레퍼런스, 비용 비교표)를 제공하는 것이 개발 기능만큼 전환에 기여합니다.
