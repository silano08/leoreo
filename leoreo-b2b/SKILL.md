# Leoreo B2B — 엔터프라이즈 게이트

`leoreo` 부록은 이렇게 적고 있습니다. **"결재를 통과시키는 기능(보안 인증, 온프레미스·VPC 옵션, 세금계산서·전자결재 연동)이 핵심 기능보다 매출 전환에 더 기여하는 경우가 흔하다."** 이 스킬이 그 기능의 실제 목록과 순서를 담당합니다.

B2B에서 매출이 막히는 지점은 대개 제품이 부족해서가 아닙니다. 실무자는 이미 설득됐는데 보안팀·구매팀·법무팀을 못 넘는 것입니다. 국내 엔터프라이즈 딜은 50~90일이 걸리고, 그 대부분이 기능 개발이 아니라 심사 통과에 쓰입니다.

## 0단계 — 먼저 확인할 것

**요청이 없는데 선제적으로 만들지 않습니다.** 엔터프라이즈 기능은 만드는 데 오래 걸리고 유지비도 붙습니다. `leoreo` 투자 게이트를 그대로 통과시킵니다.

- 지금 이것 때문에 막힌 딜이 **몇 건이고, 합쳐서 얼마인가?** 숫자가 없으면 아직 때가 아닙니다.
- 그 고객들이 **실제로 요구한 문서·기능이 무엇인가?** 추측 대신 보안질의서 원본을 받아봅니다.
- **하나의 딜만을 위한 요구인가, 반복되는 요구인가?** 한 곳만을 위한 개발은 수주 계약으로 값을 받는 게 맞습니다.
- 도입 리드타임 안에 만들 수 있는가? 못 만들면 로드맵 약속(+계약서 반영)으로 딜을 살리는 선택지가 있습니다.

## 1단계 — 딜을 여는 구현 순서

엔터프라이즈 구매자가 묻는 순서이자, 각 단계가 더 큰 딜을 여는 순서입니다. 건너뛰지 않는 편이 좋습니다.

| 순서 | 기능 | 무엇을 여는가 | 자체 구현 난이도 |
|---|---|---|---|
| 1 | **SSO** (SAML 2.0 / OIDC) | 대부분의 엔터프라이즈 도입 필수 조건. 없으면 심사 자체가 시작되지 않습니다 | 중간. IdP(사내 계정 시스템)별 편차가 큼 |
| 2 | **SCIM** (사용자 자동 동기화) | 인사 이동·퇴사자 계정이 자동 정리됨. 보안팀이 좋아하고 좌석 정산도 정확해집니다 | 중간~높음 |
| 3 | **감사로그** (고객이 직접 조회) | 보안·컴플라이언스 심사 통과의 핵심 근거 | 중간. 설계를 나중에 바꾸기 어려우니 이벤트 정의를 처음에 잘 |
| 4 | **세분화된 RBAC** (역할별 권한) | 대규모 조직의 필수 요건. IdP 그룹 → 우리 역할 매핑까지 | 중간 |

핵심 판단 두 가지입니다.

- **자체 구현 vs 구매.** `leoreo` Build vs Buy 게이트를 그대로 적용합니다 — SSO·SCIM은 차별화 지점이 아닙니다. WorkOS·Auth0류를 쓰면 몇 주가 며칠이 됩니다. 다만 고객당 과금 구조라 원가가 붙으니 `leoreo-cost` 계산에 넣습니다. 국내 공공·금융처럼 국내 리전·망분리 요건이 있으면 선택지가 제한되므로 요건을 먼저 확인합니다.
- **관리자가 스스로 설정하게 만듭니다.** SSO 연결을 우리가 매번 수동으로 해 주면 고객이 늘수록 사람이 갈립니다. 고객사 관리자가 직접 IdP 정보를 넣고 테스트하는 화면이 실질적인 확장 조건입니다.

## 2단계 — 한국 고유 게이트

해외 체크리스트에 없지만 국내에서 딜을 막는 것들입니다.

- **ISMS-P 인증**: 대기업·공공 납품에서 요구되거나 가점이 됩니다. 준비에 수개월과 실비가 들고 매년 갱신이 필요하니, 요구하는 딜 규모가 그 비용을 넘는지 먼저 계산합니다. 인증 없이도 통과하는 경우가 있으므로 "요구받았는가"를 확인하고 시작합니다.
- **보안질의서(RFP) 대응**: 고객사마다 양식이 다르지만 묻는 것은 대체로 같습니다. **한 번 잘 만든 답변 자산**(보안 백서, 아키텍처 다이어그램, 데이터 흐름도, 접근통제 정책, 사고 대응 절차)을 재사용하면 매번 며칠씩 아끼게 됩니다. 이게 개발팀이 만들 수 있는 가장 ROI 높은 문서입니다.
- **VPC·온프레미스 배포 옵션**: 금융·공공·대기업 일부는 데이터 반출을 허용하지 않습니다. 지원하기로 했다면 배포·업데이트·모니터링을 어떻게 할지가 SaaS와 완전히 달라지므로, 별도 제품으로 취급하고 가격도 따로 잡습니다. 원가는 `leoreo-cost`에 반영합니다.
- **전자세금계산서 발행**: B2B는 카드 결제보다 세금계산서 후불이 일반적입니다. 발행 연동이 없으면 경리팀에서 막힙니다. `leoreo-pay`의 결제 설계와 함께 봅니다.
- **전자결재·그룹웨어 연동**: 고객사 내부 승인 흐름에 붙는 연동이 도입 결정을 앞당기는 경우가 있습니다. 요구가 반복될 때만 검토합니다.
- **개인정보 위수탁 계약**: 고객 데이터를 처리하면 위탁 관계가 성립합니다. 표준 계약서와 재위탁(사용 중인 클라우드·SaaS) 목록을 미리 준비해 둡니다. 하위 처리자 목록을 공개 페이지로 두면 심사가 빨라집니다.

## 3단계 — 계약·운영 산출물

기능이 아니라 문서와 운영 체계로 통과하는 관문입니다. 개발팀이 만들어야 하는 것으로 환산해 둡니다.

| 요구 | 개발·운영 산출물 |
|---|---|
| SLA(가용성 보장) | 상태 페이지, 가동률 측정, 장애 공지 절차, 보상 규정 |
| DPA(데이터 처리 계약) | 데이터 보관 위치·기간, 삭제 요청 처리 기능, 하위 처리자 목록 |
| 데이터 반출·삭제 요구 | 계정 데이터 내보내기 기능, 완전 삭제 절차와 증빙 |
| 보안 사고 대응 | 사고 통지 절차와 기한, 로그 보존 기간 |
| 접근 통제 증빙 | 내부 직원의 고객 데이터 접근 로그(감사로그와 별개) |

## 4단계 — 우선순위 판단

엔터프라이즈 요구는 끝이 없습니다. 전부 만들면 로드맵이 사라지므로 게이트를 겁니다.

1. **막힌 딜 금액 합계**가 개발 원가(인일 × fully-loaded 시급)를 넘는가
2. **반복되는 요구인가** — 세 곳 이상이 물었으면 제품, 한 곳만이면 계약 협상 대상
3. **살 수 있는가** — 차별화 지점이 아니면 사는 게 기본
4. **유지비가 얼마인가** — 온프레미스는 만드는 값보다 유지하는 값이 큽니다
5. **약속으로 대체 가능한가** — 로드맵 확약과 계약 조항으로 딜을 살리고 실제 구현은 뒤로 미루는 선택지

`leoreo` 돈-체크 테이블을 그대로 채워서 판단합니다. 엔터프라이즈 기능이라고 게이트를 면제받지 않습니다.

## 출력 규칙

- 사용자와 소통할 때는 되도록 쉬운 말을 씁니다. SCIM·IdP·DPA 같은 용어가 필요하면 첫 등장에 괄호로 풀이를 붙입니다(예: SCIM(사내 계정 시스템과 사용자 목록을 자동으로 맞추는 규격), DPA(개인정보 처리 위탁 계약)).
- 요청을 받으면 **막힌 딜의 건수와 금액을 먼저 확인**합니다. 숫자가 없으면 선제 개발 대신 확인 방법을 제안합니다.
- 구현 제안은 1단계 순서(SSO → SCIM → 감사로그 → RBAC)를 근거와 함께 제시하고, 각 항목마다 자체 구현 vs 구매 판단을 함께 냅니다.
- 국내 요건(ISMS-P, 망분리, 세금계산서)은 해외 체크리스트와 구분해 별도로 짚습니다.
- 인증·규제 요건을 인용할 때는 조사 시점(2025~2026년) 기준이며 제도가 바뀔 수 있다는 단서를 붙이고, 계약·심사 전에 원문과 고객사 요구사항으로 재확인하라고 안내합니다.
- 결론은 항상 셋 중 하나입니다: **만든다 / 산다 / 계약으로 푼다** — 막힌 딜 금액과 개발 원가를 근거로.
