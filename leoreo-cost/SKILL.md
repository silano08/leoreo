# Leoreo Cost — 원가와 마진

`leoreo` 원칙 1은 "모든 개발 항목은 수익을 늘리거나, **비용을 줄이거나**, 그리로 가는 병목을 풀어야 한다"입니다. 이 스킬이 그 가운데 비용 쪽을 맡습니다.

비용 절감은 매출 증가보다 확실합니다. 매출 1,000만 원을 더 만들려면 마케팅·영업·전환이 다 맞아떨어져야 하지만, 원가 1,000만 원을 깎는 건 대체로 우리 손 안에 있고 즉시 이익으로 떨어집니다. 특히 AI 기능이 붙은 제품은 원가가 매출을 따라 같이 늘어나서, 원가를 방치하면 팔수록 마진이 줄어듭니다.

## 세 가지 원칙

1. **모르는 원가는 못 줄입니다.** 고객당·요청당 원가를 귀속시키기 전까지 절감은 감입니다. 가시화가 언제나 먼저입니다.
2. **정렬해야 할 지표는 토큰당 비용이 아니라 성공 결과당 비용입니다.** 싼 모델로 바꿔서 토큰 단가는 내렸는데 재시도가 늘면 총원가는 오릅니다. `cost-per-successful-output`(원하는 결과 하나를 얻는 데 실제로 든 돈)으로 봅니다.
3. **원가 절감도 `leoreo` 투자 게이트를 통과해야 합니다.** 월 3만 원 나가는 항목을 이틀 걸려 최적화하는 건 손해입니다. 절감액 × 12개월 vs 개발 원가로 먼저 비교합니다.

## 1단계 — 원가 가시화

무엇이 얼마나 나가는지를 고객·기능 단위로 쪼갤 수 있어야 합니다.

- **태깅 규칙을 먼저 정합니다.** 모든 클라우드 리소스와 외부 API 호출에 `service`, `env`, `feature`, `tenant`(또는 고객 등급) 태그를 붙입니다. 나중에 붙이는 건 사실상 불가능합니다.
- **원가를 세 덩어리로 나눕니다.** 고객 수에 비례하는 변동비(추론·트래픽·저장), 규모와 무관한 고정비(기본 인스턴스·라이선스), 사람 원가(fully-loaded 인건비 = 연봉의 1.25~2배). 마진 계산에는 셋 다 들어갑니다.
- **코호트별 마진을 추적합니다.** 매출은 느는데 마진이 정체되거나 나빠지면 보조금 구조입니다. `leoreo`의 쿠팡 원칙과 같은 판단입니다 — 적자가 허용되는 건 유닛 이코노믹스가 **개선 추세**일 때뿐입니다.
- 원가 지표를 대시보드에 올리는 방법은 `leoreo-metrics`가 담당합니다. 매출 지표 바로 옆에 같은 기간·같은 코호트 기준으로 둡니다.

## 2단계 — LLM 추론 원가 절감 사다리

효과가 크고 리스크가 낮은 순서입니다. 위에서부터 하고, 아래로 갈수록 품질 검증이 더 필요합니다. 2026년 보고 기준으로 이들을 조합하면 관리형 API 지출의 50~90%를 줄인 사례가 나옵니다.

| 순서 | 기법 | 예상 절감 | 품질 리스크 | 언제 |
|---|---|---|---|---|
| 1 | **프롬프트 캐싱** | 재사용 구간에 최대 ~90% 할인 | 없음 | 시스템 프롬프트·문서·예시가 반복될 때. 사실상 공짜 절감이라 제일 먼저 |
| 2 | **모델 라우팅** | 30~60% | 낮음~중간 | 쉬운 질의를 작은 모델로 보내고 어려운 것만 큰 모델로. 난이도 분류가 관건 |
| 3 | **배치 처리** | 배치 API 사용 시 약 50% | 없음 | 즉시 응답이 필요 없는 작업(요약·분류·색인) |
| 4 | **컨텍스트 압축** | 20~50% | 중간 | 대화 이력·문서를 통째로 넣지 않고 요약·검색으로 필요한 부분만 |
| 5 | **출력 길이 제어** | 10~30% | 낮음 | 출력 토큰이 입력보다 비쌉니다. 구조화 출력·최대 토큰 제한 |
| 6 | **셀프호스팅·양자화** | 규모가 크면 큼 | 높음 | 운영 부담과 GPU 고정비가 따라옵니다. 물량이 확실해진 다음에만 |

실행 순서 규칙입니다.

- **1·3번(캐싱·배치)부터 합니다.** 정확도 리스크가 0이라 검증 부담이 없습니다.
- **2·4번은 반드시 품질 평가와 함께 갑니다.** 바꾸기 전에 대표 입력 세트로 정답률을 재고, 바꾼 뒤 같은 세트로 다시 잽니다. 재시도율·실패율이 오르면 절감이 아니라 이전입니다.
- **6번은 마지막입니다.** GPU 고정비와 운영 인건비가 관리형 API 비용을 넘는 지점이 오기 전엔 손해입니다. `leoreo`의 Build vs Buy 기본값("먼저 사고, 필요해지면 만든다")이 그대로 적용됩니다.

## 3단계 — 클라우드 FinOps

- **Inform → Optimize → Operate** 순서입니다. 비용을 보이게 만들고(태깅·대시보드), 낭비를 걷어내고, 예측을 개발 프로세스에 심습니다.
- **배포 전에 비용을 추정합니다.** 인프라 코드 단계에서 증분 비용을 뽑아 PR에 붙이면(Infracost류) 배포 후 청구서에 놀라는 일이 없어집니다. `leoreo` 돈-체크 테이블의 "인프라 증분 ₩/월" 칸을 이 숫자가 채웁니다.
- **가장 흔한 낭비**는 늘 비슷합니다. 쓰지 않는 개발·스테이징 환경이 24시간 떠 있음, 과대 스펙 인스턴스, 붙어 있지 않은 디스크와 오래된 스냅샷, 로그·모니터링 보관 기간 과다, 리전 간 트래픽, 예약 할인 미적용.
- **상시 예산 알림을 켭니다.** 월 예산의 50/80/100% 지점에서 알림이 오게 합니다. 사후에 아는 비용은 이미 나간 비용입니다.
- 국내 환경(NCP·KT클라우드 등) 항목별 점검표는 `references/cloud-finops.md`에 있습니다.

## 4단계 — 마진 게이트

원가를 깎을 만큼 깎았는데도 마진이 목표 아래면 그건 원가 문제가 아니라 가격 문제입니다.

| 제품 유형 | 총마진 기준선 (2025~2026년 조사 기준) |
|---|---|
| 전통 SaaS | 75~85% |
| AI 기능이 붙은 제품 | 50~60% (2026년 조사 평균 약 52%) |
| 마켓플레이스·중개 | 수수료 수익 기준으로 별도 계산 |

판단은 이렇게 갈립니다.

- **마진이 기준선 아래이고 원가에 손댈 여지가 남았다** → 2·3단계 사다리를 더 내려갑니다.
- **원가를 다 깎았는데도 아래다** → 가격 또는 과금 단위 문제입니다. `leoreo-model`로 넘깁니다. 정액제인데 사용량 편차가 크면 크레딧·오버리지로 분리하는 게 정석이고, 사용자당 월 AI 원가가 아주 작으면 번들에 묶는 게 낫습니다.
- **특정 고객군만 마진이 음수다** → 그 세그먼트의 가격·플랜을 따로 잡거나 받지 않습니다. 전체 평균 마진은 이 문제를 가립니다.
- **추론 원가가 CAC 회수기간을 망가뜨린다** → 매출이 늘수록 원가도 느는 구조라 회수기간 계산에 반드시 원가를 넣어야 합니다. 총마진을 반영하지 않은 LTV:CAC는 실제보다 좋아 보입니다.

## 출력 규칙

- 사용자와 소통할 때는 되도록 쉬운 말을 씁니다. FinOps·양자화 같은 용어가 필요하면 첫 등장에 괄호로 풀이를 붙입니다(예: 프롬프트 캐싱(반복되는 앞부분을 재사용해 값을 깎는 것), 양자화(모델을 가볍게 만들어 싸게 돌리는 것)).
- 절감 요청이면 **현재 원가 구조를 먼저 확인**합니다. 모르면 1단계 가시화부터 제안하고, 추측으로 최적화를 시작하지 않습니다.
- 절감안은 항상 **예상 절감액 · 품질 리스크 · 개발 비용**을 함께 적어 사다리 순서대로 냅니다. 절감액 × 12개월이 개발 원가보다 작으면 하지 말자고 말합니다.
- 품질에 영향을 주는 기법(모델 교체·압축)을 제안할 때는 반드시 사전·사후 평가 방법을 같이 냅니다.
- 수치를 인용할 때는 조사 시점(2025~2026년) 기준이라는 단서를 붙입니다. 모델 단가와 할인 정책은 자주 바뀌므로 적용 직전 공식 가격표로 재확인하라고 안내합니다.
- 결론은 항상 셋 중 하나입니다: **원가를 깎는다 / 가격을 손본다(leoreo-model으로) / 지금은 그대로 둔다** — 근거 숫자와 함께.
